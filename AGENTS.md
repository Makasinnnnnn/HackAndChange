## Решения владельца от 12.11.2026

- Ведём весь проект; владелец поможет с человеческой оценкой рекомендаций.

## Данные и честность

- Никогда не коммитить дамп, SQL, производные реальные каталоги, пользовательские данные, индексы реального каталога, `.env`, токены, ключи. Всё это только в `.private/` или закрытых томах.
- Не отправлять исходные данные, платные уроки и персональные сведения внешним LLM, включая бесплатные модели и помощников в терминале.
- Исходные таблицы не менять. Нормализация в отдельном хранилище, импорт read-only. Статус публикации, ограничения подписок и цена — разные признаки. Организаторы уточнили: именно `Courses.Cost IS NULL` означает бесплатный курс; не обобщать на другие таблицы. Импорт нормализует такую цену в 0, но сохраняет подписочные ограничения; тарифная цена не подменяет цену курса (см. `docs/organizer-clarifications.md`).
- Не рендерить исходные HTML/JS. Только экранированный текст и проверенные HTTP(S)-ссылки.
- Не придумывать URL, длительность, цену, опыт, просмотры или результаты evaluation. Неизвестные поля nullable. Синтетика помечена DEMO в API и UI.
- Изолированная аудиторская БД имеет метки `project=hackandchange`, `purpose=private-data-audit`, без портов и с `--network none`. Не запускать очистку чужих контейнеров/томов.
- Публичное демо использует только авторские синтетические материалы. Платные материалы: краткое описание пользы и ссылка, без тела уроков.

## Разработка и проверка

- Малые законченные итерации: сквозной сценарий → персонализация → оценка → полировка.
- Baseline независим от персональных весов. Одинаковые каталог, фильтры доступности и запрос при сравнении.
- Реальные основания объяснений должны совпадать с использованными сигналами. Если признак неизвестен, не утверждать его использование.
- Семантическую модель считать опциональной, пока её качество и запуск не проверены. Лексический поиск не называть нейросемантическим.
- После изменений алгоритма запускать unit/API tests. После UI — typecheck, build и браузерные E2E, включая мобильный экран. Docker проверять реальным запуском, повторным стартом и сохранением прогресса.
- Команды проверки и запуск находятся в README; не считать ещё не существующие команды рабочими.
- Evaluation: раздельные наборы настройки и проверки, происхождение меток, версия каталога, реальные рассчитанные метрики. Автоматические метки не выдавать за экспертные.
- Не устанавливать плагины ради количества. Использовать имеющиеся инструменты, ставить только необходимые зависимости с фиксированными версиями.
- Внешнему помощнику можно передавать только явно перечисленные публичные файлы и синтетические fixtures; результаты проверяет основной разработчик. Не предполагать бесплатность провайдера и не запускать платную модель без решения владельца.
- Tutor mode проверяется через `~/.tutor-mode/projects.json` для текущего пути и его предков. На старте 12.11.2026 здесь OFF.

## Критерий готовности

Основной сценарий работает; baseline и персонализация действительно рассчитываются; полный режим проверен на реальном дампе; demo не требует дампа или ключей; есть объяснения, cold start, feedback, оценка, Docker, README, PDF-презентация и сценарий защиты. Невыполненные пункты явно перечислять в `docs/STATUS.md`.

## Алгоритм после полного рефакторинга

Текущая рабочая ветка audit/pr-1-stability, pipeline v6 / релиз 1.2. Сначала прочитать docs/recommendation-pipeline.md. Правила предметной области держать в recommendation/intent.py, жёсткие исключения в eligibility.py, веса/версии в policy.py; не добавлять разрозненные проверки конкретных пользовательских фраз в engine.py или frontend. Фильтровать до оценки confidence; baseline разделяет query constraints, но не личную историю/профиль. General scope определяется по показанным карточкам, не по всему пулу; общая подборка максимум 3. Любое изменение поведения — версия и новые регрессионные проверки. Исторические benchmark/метрики не выдавать за текущие.

Ограничение рекламного бюджета выделяется в intent как fixed_ad_spend. Общая метка маркетинга недостаточна: eligibility требует механизм из названия/описания; объяснения и предлагаемые действия формируются в explanation.py. Без указанной отрасли не подставлять специализированные marketplace/другие отраслевые статьи. Не выдавать glossary вместо практических материалов; constrained shortlist <=3 и относительный порог. Это контролируемые правила, не универсальное понимание отрицаний.
