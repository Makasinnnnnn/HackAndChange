# Работа в команде и запуск AI-агента

## Что получить из Git

Общий комплект находится прямо в репозитории. Никакие файлы из домашней папки владельца или его `.codex` копировать не нужно.

| Файл | Назначение |
|---|---|
| `../AGENTS.md` | Единые правила проекта, данных, Git, проверок и сдачи |
| `../backend/AGENTS.md` | Контракт API, подбор, сессии и проверки backend |
| `../frontend/AGENTS.md` | Интерфейс, асинхронные ответы, доступность, E2E |
| `../scripts/AGENTS.md` | Импорт, аудит, evaluation и безопасная упаковка |
| `AGENTS.md` | Актуальность документации и источники утверждений |
| `../CLAUDE.md`, `../GEMINI.md`, `../.github/copilot-instructions.md` | Короткие входные файлы, отсылающие к общим правилам |
| `STATUS.md`, `NEXT.md`, `plan.md`, `worklog.md` | Состояние, приоритеты, очередь и передача работы |
| `assistant-tasks.md` | Ограничения и задания для дополнительного помощника |

Не все инструменты одинаково загружают инструкции. Надёжный вариант — явно попросить агента прочитать корневой AGENTS.md и ближайший AGENTS.md в изменяемом каталоге. Не добавлять отдельную копию правил для каждой модели.

## Первый запуск

Из папки, где будет храниться проект:

```powershell
git clone https://github.com/Makasinnnnnn/HackAndChange.git
cd HackAndChange
git switch -c work/your-name/task
docker compose up -d --build
```

Открыть http://127.0.0.1:3080. Нужен Docker Desktop с Linux containers. Первая сборка требует доступа к реестрам зависимостей. DEMO содержит авторские примеры и работает без закрытого дампа, E5, Qwen и API-ключей. Наличие FULL и моделей на машине владельца не означает, что они есть у участника.

Если проект уже клонирован, сначала проверить `git status`, сохранить свою работу и обновить ветку обычным Git-процессом. Не использовать `reset --hard` для синхронизации. Уже опубликованные теги не переписывать.

## Native-проверки, если меняешь код

Для команд Python/npm вне контейнеров нужны Python 3.13 и Node.js 24. Пример для Windows при наличии Python Launcher:

```powershell
py -3.13 -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
npm --prefix frontend ci
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m ruff check backend scripts
npm --prefix frontend run typecheck
```

Если окружение уже есть, не пересоздавать его без необходимости. На другой ОС использовать соответствующий путь к Python из venv. Команды `python ...` в документации предполагают активированное подходящее окружение; на Windows можно явно указывать `.venv/Scripts/python.exe`.

Тесты не требуют закрытого дампа. Проверка реальной E5 опциональна и пропускается без локальных весов; это не прохождение FULL-проверки. Production build: `npm --prefix frontend run build`. Остальные команды и настройки — в [README](../README.md).

## Отдельный экземпляр для E2E

Не запускать E2E против рабочего FULL или чужого экземпляра: тесты создают отметки и импортируют синтетическую историю. В отдельном терминале из корня, выбрав свободный порт и уникальное имя Compose-проекта:

```powershell
$env:WEB_PORT='3090'
docker compose -p hac-team-your-name --env-file .env.example up -d --build --wait --wait-timeout 240
$env:E2E_BASE_URL='http://127.0.0.1:3090'
npm --prefix frontend run test:e2e
.venv/Scripts/python.exe scripts/smoke.py --base http://127.0.0.1:3090
docker compose -p hac-team-your-name --env-file .env.example down
```

Для E2E нужен Chrome; установка браузера, используемая CI: `npx playwright install chrome` из `frontend/`. Переменные выше действуют в текущем терминале. Обычный `down` сохраняет тестовый том. Не добавлять `-v` к чужому/рабочему проекту; удаление своего тестового тома допустимо после проверки имени и Compose-меток.

## Разделение задач

- Одна задача — одна ветка и понятная область файлов. В разных задачах не редактировать одни и те же файлы одновременно в общем checkout; при необходимости использовать отдельные checkout/worktree.
- До начала прочитать STATUS/NEXT и последние записи worklog, проверить ветку и незакоммиченные изменения. Согласовать пересекающиеся изменения с участником, не затирать их автоматически.
- Перед merge показать diff и фактические проверки. Без write-доступа участник может подготовить PR из своего fork. Прямой push в main возможен только по явному поручению владельца.
- После изменения подбора проверить положительные и отрицательные примеры, baseline и неполный профиль. Нельзя чинить один запрос привязкой к конкретному source ID.
- Отчёт по задаче: проблема → изменение → выполненные проверки → ограничения/следующий шаг. Отдельно назвать проверки, которые не выполнялись.
- Публиковать только публичный код, документацию, синтетические fixtures и DEMO-изображения. `.private/`, `.env`, модели, реальная история и подробные выдачи не входят в PR.
- После фактической отправки организаторам main и отправленный тег сохраняются; работа продолжается только в `post-submission/...`. Сверить актуальный статус с владельцем. Локальный `submitted=false` не доказывает отсутствие отправки с другой машины.

## Стартовый запрос своему агенту

> Прочитай AGENTS.md, docs/STATUS.md, docs/NEXT.md, docs/TEAM.md и последние записи docs/worklog.md. Перед изменениями прочитай AGENTS.md в нужном каталоге. Проверь текущую ветку и локальный diff; сохрани работу других участников. Моя задача: [описание]. Разрешённая область: [файлы/модули]. Критерий готовности: [наблюдаемое поведение]. Используй DEMO и синтетические fixtures; закрытые данные и секреты не публикуй и не передавай сторонним AI. Воспроизведи проблему, внеси минимальное законченное изменение, выполни подходящие проверки, обнови статус и журнал. В отчёте укажи фактические результаты и оставшиеся ограничения. Не выполняй деплой, сдачу, платные вызовы и сообщения людям без отдельного разрешения.

## Перед передачей работы

```powershell
.venv/Scripts/python.exe scripts/check_public_files.py
.venv/Scripts/python.exe scripts/check_version.py
git diff --check
git diff --cached --stat
```

Эти проверки не заменяют просмотр staged diff. В PR указать сценарий проверки и режим каталога. Если менялась только документация, достаточно проверить ссылки, инструкции и публикационную безопасность; не писать, что приложение повторно протестировано.
