## 2. Прогрев весов (чтобы демо не висело на скачивании)

**Факт, который надо знать точно:** проект использует **`Xenova/multilingual-e5-small`, ONNX INT8,
384 измерения** — не BGE-M3. BGE-M3 (~2.3 ГБ) и `bge-reranker-v2-m3` в проекте **не реализованы**; это
предложения из прошлого аудита (P2), не текущая функциональность. Не обещать их на показе.

- [ ] Где лежат веса: `./.private/models/e5` на хосте, монтируется в контейнер **read-only** как
      `/models/e5` (`compose.semantic.yaml`). Named volume для модели не используется.
      `~/.cache/huggingface` внутри контейнера — временный, на него не рассчитывать.
- [ ] Прогрев заранее (одна команда, скачивает публичные веса, ключ не нужен):

      ```bash
      docker compose -f compose.yaml -f compose.semantic.yaml --profile models run --rm model-download
      ```

      Скрипт `scripts/download_model.py` фиксирует ревизию `761b726dd34fb83930e26aab4e9ac3899aa1fa78`
      и пишет `manifest.json` с SHA-256 по файлам. Он пишет **в `.private/models/e5`**, а не в `/models/e5` —
      поэтому монтирование в overlay совпадает.
- [ ] Проверить, что папка не пустая: `ls -la .private/models/e5` → `onnx/model_quantized.onnx`,
      `tokenizer.json`, `tokenizer_config.json`, `config.json`, `manifest.json`.
      **⚠️ не проверено в этой сессии**: в рабочей среде `.private` отсутствует.
- [ ] Запуск с семантикой (второй терминал/вторая команда, отдельно от `up`):

      ```bash
      docker compose -f compose.yaml -f compose.semantic.yaml up --build -d
      curl -s http://127.0.0.1:3080/api/bootstrap
      # ожидаемо: "semantic_model": "<id модели>", "semantic_fallback": false
      ```

      Для семантического варианта `api` healthcheck: `start_period 180s`, `retries 60` — первый старт
      заметно дольше, это норма.
- [ ] Если папка модели не подготовлена — bind mount упадёт на старте. Лечение: выполнить команду
      загрузки (выше) **или** вернуться к обычному стеку `docker compose up -d --build`.
- [ ] Offline-режим: `HF_HUB_OFFLINE=1` уже выставлен в overlay, то есть после прогрева сеть не нужна.
- [ ] Если очень хочется BGE-M3/reranker на показе — **не в этой сессии**: нужен отдельный образ
      (+~2 ГБ зависимостей `sentence-transformers`/torch), отдельная ветка и замер p95. На CPU это
      секунды на запрос. Не обещать.

## 5. Три сценария из Приложения 2 — по одной команде на каждый

Ниже — `curl` через прокси фронта с cookie-банкой (сессия посетителя живёт в cookie `route_session`).
Все ожидаемые значения помечены `[static, manual-sim, DEMO-36]`: получены воспроизведением
`parse_intent`/`exclusion_reason` и TF-IDF на **фактическом коде** проекта, без запуска Docker.
Live-прогон здесь не выполнялся — на показе сверять факт с ожиданием и записывать отклонения.

Подготовка (один раз в терминале):

```bash
export J=/tmp/hac-cookies.txt
curl -s -c $J -b $J http://127.0.0.1:3080/api/ready
```

### S1. Новый пользователь, задача «продвижение бизнеса»

```bash
curl -s -c $J -b $J -X POST http://127.0.0.1:3080/api/recommendations \
  -H 'Content-Type: application/json' \
  -d '{"query":"нужно продвигать бизнес","limit":3}' | python -m json.tool
```

**Ожидаемо:** HTTP 200, `items` = **2 карточки** (demo-marketing-podcast «Как предприниматель
проверяет идеи продвижения», demo-local-promo «План локального продвижения на неделю»),
у каждой — непустые `reasons` (реальное основание), `next_action` (следующий шаг), `phase`.
`clarification` отсутствует. `excluded_count`/`candidate_count` — диагностика.

- [ ] На экране: две карточки с объяснением и «следующим шагом», без пустого состояния.
- [ ] Отклонение от ожидания зафиксировать (сколько карточек реально, есть ли notice).

### S2. Повторный визит с фидбеком

Сидов нет: свежая БД пустая (`rg seed backend scripts` — совпадений нет). Историю создаём сами.

```bash
# 1) первичный запрос (тот же, что S1 — там 2 карточки, чтобы было что исключать)
curl -s -c $J -b $J -X POST http://127.0.0.1:3080/api/recommendations \
  -H 'Content-Type: application/json' -d '{"query":"нужно продвигать бизнес","limit":3}' > /tmp/s2-before.json

# 2) взять id первой карточки
python -c "import json;print(json.load(open('/tmp/s2-before.json'))['items'][0]['material']['id'])"

# 3) отметить «изучено» и «полезно»
curl -s -c $J -b $J -X POST http://127.0.0.1:3080/api/feedback \
  -H 'Content-Type: application/json' -d '{"material_id":"<ID_ИЗ_ШАГА_2>","signal":"completed"}'

# 4) повторить запрос
curl -s -c $J -b $J -X POST http://127.0.0.1:3080/api/recommendations \
  -H 'Content-Type: application/json' -d '{"query":"нужно продвигать бизнес","limit":3}' | python -m json.tool

# 5) прогресс должен сохраниться
curl -s -c $J -b $J http://127.0.0.1:3080/api/progress | python -m json.tool
```

**Ожидаемо:** на шаге 4 отмеченный материал **исчезает** из выдачи (остаётся 1 карточка);
`/api/progress` содержит его с `signal: completed`; отметка сохраняется после перезапуска сервисов.
Если исключить все карточки — вернётся `clarification` «Подходящих доступных материалов не осталось…»,
это корректное поведение, а не баг.

- [ ] Сделать то же в UI: «Изучено» → перестроить → материал пропал, в «Мой прогресс» остался.
- [ ] **Ловушка демо:** не выбирать для S2 запрос с одной карточкой (например, «нужно привлечь клиентов
      в кофейню» → 1 карточка): после отметки экран станет пустым, и это будет выглядеть как поломка.

### S3. «Точного совпадения нет»

```bash
curl -s -c $J -b $J -X POST http://127.0.0.1:3080/api/recommendations \
  -H 'Content-Type: application/json' \
  -d '{"query":"Яндекс.Директ для салона красоты","limit":3}' | python -m json.tool
```

**Ожидаемо (текущее поведение, честно):** `items: []` и `clarification` вида «Пока определена только

«Налоговый режим», relevance 0.082–0.126) — то есть даже потенциальная выдача была бы нерелевантной.

- [ ] На показе сказать вслух: «точного материала нет, поэтому система задаёт уточняющий вопрос;
      это осознанное ограничение, а не слив».
- [ ] Второй пример честного отказа: `{"query":"как настроить kubernetes кластер","limit":3}` →

## 6. Если LLM API недоступен

- [ ] `LLM_MODE` по умолчанию **`off`** (`backend/app/llm.py:82`). Тогда `POST /api/intent` возвращает
      `{"status":"disabled","intent":null}`, панель «Предложение AI» в UI просто не появляется,
      маршрут строится правилами. **Сообщения об ошибке пользователь не видит — и не должен.**
- [ ] Проверка одной командой:

      ```bash
      curl -s -X POST http://127.0.0.1:3080/api/intent \
        -H 'Content-Type: application/json' -d '{"query":"хочу открыть кофейню"}' | python -m json.tool
      # ожидаемо: {"status":"disabled","intent":null}
      ```

- [ ] Возможные статусы (все — «деградация без падения»): `disabled`, `model_missing`,
      `configuration_blocked`, `invalid_configuration`, `unavailable`, `invalid_response`, `unchanged`, `ready`.
      При `unavailable` UI показывает «AI не нашёл более точной формулировки…», маршрут по тексту
      пользователя продолжает работать.
- [ ] **Ранжирование от LLM не зависит вообще.** LLM используется только в `/api/intent`
      (переформулировка + один вопрос). Поэтому «LLM упал» ≠ «ухудшился retrieval».
- [ ] Кеша ответов LLM нет — это нормально, потому что LLM не в критическом пути.
- [ ] Отдельная ось: если нет **весов E5**, ранжирование деградирует до лексики (TF-IDF) — на это
      указывает `semantic_fallback: true` в `/api/bootstrap`. Не путать с недоступностью LLM.
